## Pivotal decisions taken

- **Decision A (probe catalog layout — single file vs. one-folder-12-entries vs. per-control subdirectory): one folder `src/agents/sandbox-runner/probe-primitives/` with 13 sibling entry files (cc-11-1.ts, cc-11-2.ts, cc-11-4.ts, cc-11-6.ts, cc-11-9.ts, cc-11-12.ts, cc-11-13a.ts ... cc-11-13e.ts, plus cc-11-3.ts moved from the step-39 file) + one `index.ts` that builds `PROBE_PRIMITIVE_CATALOG` from the 13 imports.** Runner-up (REJECTED): extend the existing single `probe-primitives.ts` with 12 more constants. Tradeoff: FPP §2A's "one folder per service identity" principle here treats the *control* as the identity-equivalent — adding cc-11-14 in a future phase should be one new file, not an edit to a thousand-line shared module. Per-control subdirectories with co-located tests are runner-up #2 (REJECTED) — over-fragmentation when the per-control file is itself <100 lines; tests can co-locate as `probe-primitives/cc-11-N.test.ts` siblings if useful. The `index.ts` is the SOLE place that calls `new Map(...)` (mirrors step 39's pattern of one map per catalog); adding a 14th entry is a one-line `import` + Map entry.

- **Decision B (AI-authored vs. fixed fields per control — minimize AI surface): every probe has `method` + `urlTemplate` + `bodySchema` SHAPE fixed; AI-authored fields are limited to (i) `pathParams.<name>` for templated URL segments (cc-11-3 IDOR pattern; cc-11-13a–e clone this), (ii) `queryParams.<name>` for cc-11-13c (cross-tenant filter bypass requires AI to author a tenant-id value to pollute), (iii) `bodyFields.<name>` for cc-11-4 (client-supplied tenant_id override). All other fields are `fixed`.** Runner-up (REJECTED): leave URL paths fully AI-authored. Tradeoff: step 39 preventer-9 amended — "AI authors parameters + request shape WITHIN `requestSchema`; AI does NOT invent new executable test types." Each control's `urlTemplate` IS the test type; letting AI author the URL means letting AI invent the test. The per-control table in Produces below pins this contract control-by-control.

- **Decision C (source of AI-authored values — typed row-handles NOW vs. open strings + 40f additive): probes accept OPEN-STRING `path_params` / `query_params` / `body_fields` values in this step. 40f later adds an optional `row_handle?: string` field that the runtime resolves to the underlying value before sending.** Runner-up (REJECTED): require typed row-handles immediately and block 39b on 40f. Open strings keep 40f purely additive (a new optional arg that, when present, takes precedence over the open string and the AI gets a higher-fidelity input source). Step-39 invariants (regex-bounded length caps on AI-authored strings per `pathParams.id`'s `z.string().min(1).max(64).regex(/^[a-zA-Z0-9-]+$/)`) carry forward — the Zod schema is what bounds the surface, not the source.

- **Decision F (cleanup discipline per probe — `audit_only` vs. `reverse`): the 7 GET-only probes (cc-11-1, cc-11-2, cc-11-4-GET-variant, cc-11-6, cc-11-9, cc-11-12, cc-11-13a) use `cleanup_strategy: 'audit_only'` (40c-v3 Decision G.5); the 5 mutating-or-fixture-synthesizing probes (cc-11-4-POST-variant, cc-11-13b, cc-11-13c, cc-11-13d, cc-11-13e) AND the synthetic-fixture-row probes (cc-11-13a–e when they create test rows in addition to reading) use `cleanup_strategy: 'reverse'` with Path-2 admin entries for the fixture-row creates.** Runner-up (REJECTED): mark every probe `audit_only` and treat fixture creation as an out-of-band synthesize-actor responsibility. - **Decision G (Mode A vs. Mode B applicability — codex 39b-001 [APPLIED]): ALL 12 migrated probes are Mode-B-only (`sandbox_active_validation`).** Runner-up (REJECTED): the v1 of this decision granted 3 probes (cc-11-1, cc-11-12, cc-11-13a) Mode-A applicability via a `'read_code'` override. Tradeoff: codex caught the trust-model violation — `read_code` is a LOCAL filesystem-read action for the user's project; using it to authorize OUTBOUND HTTP probes (to the deployed app, PostgREST, or Storage) conflates two distinct trust axes. `read_only_evidence` mode is supposed to be safe in any environment (CLAUDE.md §Validation policy: "Safe for any environment. Reads code, schema metadata, storage metadata via MCP, scanner outputs. Never mutates."). An outbound HTTP probe — even an anon one — observably touches the target system; in production that is exactly what `read_only_evidence` is meant to forbid. The clean fix: every probe-http invocation is an active-validation action gated by `'call_api_with_test_identity'`, only present in `sandbox_active_validation`'s `allowed_actions`. Under Mode A, all 12 probes deny at the policy gate; the floor emits `coverage_gap` findings for the missing active evidence. An operator who wants probe coverage runs Mode B with a sandbox. (If a future phase introduces an `'active_read_probe'` AllowedAction with environment-restricted semantics, that's a separate deliberate policy-axis decision — explicitly NOT 39b's scope.)

- **Decision H (per-probe declared capability set — codex 39b-002 + 39b-003 [APPLIED]): `requiredActions: readonly AllowedAction[]` on each `ProbePrimitive` + a `requiredActionForArgs(args): readonly AllowedAction[]` dynamic-gate hook on `ToolDescriptor`.** Runner-up (REJECTED): the v1 of this decision used a single `requiredActionOverride?: AllowedAction` field. Codex caught two issues: (i) the loop's policy gate runs BEFORE args parsing, so looking up `args.probe_id` to derive the action requires either gate-order rework or in-tool re-check; (ii) the single-action shape doesn't cover the 5 mutating probes that need `create_synthetic_record` (synthesize fixture rows) AND `cleanup_veyra_created_data` (delete them) AND `call_api_with_test_identity` (send the test request) — a policy that grants only the last would still allow row synthesis. The two-part fix:

  - **Per-primitive declaration:** each `ProbePrimitive` declares `requiredActions: readonly AllowedAction[]` listing EVERY capability the probe needs. The 7 GET-only probes declare `['call_api_with_test_identity']`. The 5 mutating probes (cc-11-4 POST-variant, cc-11-13b, cc-11-13c, cc-11-13d, cc-11-13e — per Decision F) declare `['call_api_with_test_identity', 'create_synthetic_record', 'cleanup_veyra_created_data']`. Adding a 14th probe is one Map entry.
  - **Dynamic-gate hook:** `ToolDescriptor` gains an optional `requiredActionForArgs?: (args: A) => readonly AllowedAction[]` field. When set, the loop policy gate runs the args schema parse FIRST (already happens before invoke), then resolves the primitive from the parsed `args.probe_id`, reads its `requiredActions`, and enforces ALL declared actions against `policy.allowed_actions`. Any missing → deny. Unknown `probe_id` → deny (gate-side, before invoke). The descriptor's static `required_action` stays as the FLOOR (the minimum any effective set must contain); `probe-http`'s static `required_action` is `'call_api_with_test_identity'`. The hook is purely additive — descriptors that don't declare it work exactly as before (40c-v3-compatible).

  V6 tests: (a) policy with `{call_api_with_test_identity}` denies cc-11-4 (which also needs `create_synthetic_record` + `cleanup_veyra_created_data`) at the gate, BEFORE invoke runs; registry untouched. (b) policy with all three actions allows cc-11-4 at the gate. (c) unknown `probe_id: 'cc-11-99-fake'` denies at the gate, not silently 404 inside invoke. (d) the hook fires AFTER schema parse but BEFORE `enforce(...)` — assert via trace `gate_decision` row at `arg_validation: 'accepted'` + `gate_decision: 'deny'`.
