## Pivotal decisions taken

- **Decision A (hypothesis shape — REUSE vs. fresh): define a fresh `LoopHypothesis` in `src/cli/hypothesis-registry/types.ts`; do NOT import the existing `src/types/hypothesis.ts` `Hypothesis`.** Runner-up (REJECTED): reuse `src/types/hypothesis.ts` `Hypothesis` directly. Tradeoff: the existing Phase-2 type carries `ScanFactRef[]`, `ContextRequest`, `BlastRadius`, and a closed `ProposedFindingType = 'likely_issue' | 'informational'` union — all shaped around the deprecated AI Inference Agent's facts-grant lifecycle. The loop's hypothesis is *iterative AI orchestration metadata* with a different lifecycle (`proposed` / `partially_evidenced` / `evidenced_against` / `superseded`), a different evidence link (`briefing_field_ref` + `step_refs` to accepted loop steps, NOT `ScanFactRef`), and explicitly NO `proposed_finding_type` field (the trust-model constraint says hypotheses are NOT findings — surfacing a "type" field invites operators to read them as classifications). Importing the Phase-2 shape would force every consumer to handle fields the loop never populates, and would re-open §D.1 boundary questions about `ScanFactRef`. The Phase-2 `Hypothesis` stays where it is (no edits); 40e's fresh `LoopHypothesis` is the layer-appropriate shape. FPP §2A: `LoopHypothesis.control_id_hint?: string` stays a freeform string with `confidence`, never a closed union.

- **Decision B (registry location — `src/cli/` vs. `src/core/`): one leaf folder `src/cli/hypothesis-registry/`.** Runner-up (REJECTED): `src/core/orchestrator/hypothesis-registry/`. Tradeoff: 40d's Decision B established the precedent — anything that imports from `src/agents/` (the briefing module pulled `redactSecrets` + the AI provider seam) cannot live under `src/core/` without violating the `no-cross-layer-imports` invariant at `src/types/no-cross-layer-imports.test.ts:10-11,92-103`. 40e's registry impl itself is small and could in principle live under `src/core/` — but two pressures push it into `src/cli/` regardless: (i) the propose-hypothesis descriptor needs to redact the AI-authored `statement` field via the same `Redactor` chokepoint (`src/ai/ai-output-redaction.ts`, which is under `src/ai/`), (ii) Phase 4 sibling registries (e.g. `evidence-trail-registry`) will follow the same pattern. The TYPES (`LoopHypothesis`, `HypothesisDisposition`, `HypothesisId` brand) live in `src/cli/hypothesis-registry/types.ts`; `LoopView.hypotheses?` in `src/core/orchestrator/artifact-state.ts` imports them via `import type` (erased at runtime, layer-safe — same dodge 40d uses for `ProjectBriefing`).

- **Decision C (registry ownership — `ArtifactState` field vs. separate registry instance): separate `HypothesisRegistry` instance threaded via closure.** Runner-up (REJECTED): mutate via dedicated `ArtifactState` methods (e.g. `state.recordHypothesis(...)`, mirroring `state.recordProbeAttempt()`). Tradeoff: `ArtifactState` is the append-only loop-record log; adding mutation methods for an in-loop AI-mutable registry mixes two concerns (immutable event log vs. mutable hypothesis state with disposition transitions). The 40c-v3 `ActorSecretRegistry` pattern (`src/core/sandbox/actor-secret-registry.ts`) — closure-injected, instance owned by the loop driver in `scan-command.ts`, surfaced to `proposeNext` as a `LoopView` projection only — is the F3-stability shape every Phase-3 in-loop mutable state uses. Same `try/finally` ownership: the loop driver constructs the registry at branch start and persists `hypotheses.json` (success path) in the existing scan-end persistence block. `ToolContext` (`{scanId, projectPath, artifactDir}`) stays unchanged.

- **Decision D (args validation — two-layer prewrite guard; codex 40e-prewrite-guard-incomplete-and-v4-mis-specified [APPLIED]): two layers, BOTH running BEFORE any registry mutation.** Runner-up (REJECTED): single recursive `containsClassificationKey` walk on the whole args. Tradeoff: codex caught that `containsClassificationKey` checks object KEYS + `NamedFact.name` strings (per `src/types/tool-result.ts:83-103`), but it does NOT check scalar string VALUES. A propose-hypothesis call with `args: {statement: "finding_type: launch-blocker", confidence: 'medium'}` would pass both Zod strict-object (statement is an allowed string field) AND the recursive deny-walk (no object key is a classification key). The two-layer fix:
  - **Layer 1 (schema):** Zod `strictObject` rejects unknown top-level fields BEFORE invoke runs (catches smuggle attempts like `args.finding_type` or `args.evidence_refs[].kind` — the loop already records `arg_reject` at this boundary via existing tool-call infrastructure).
  - **Layer 2 (prewrite scalar denylist, NEW for 40e):** inside `tool.invoke`, BEFORE the registry mutates, walk the AI-authored scalar string fields (`statement`, `statement_addendum`) through a `containsClassificationStringToken` helper (the same 10-token denylist 40d defined inline — pull it into `src/cli/hypothesis-registry/validate.ts` as a reusable export). Any hit returns `Result.err(ClassificationKeyInArgsError)` and the invoke records `tool_result_reject` (loop-trace path; registry untouched). The recursive `containsClassificationKey` walk also runs as belt-and-suspenders (in case the args schema ever loosens). V4 below tests scalar-smuggling specifically; V4b tests the recursive walk.

- **Decision E (AllowedAction surface — new action vs. reuse existing; codex 40e-allowed-action-read-code-does-not-hold [APPLIED]): add ONE new `'author_hypothesis'` AllowedAction.** Runner-up (REJECTED): reuse `'read_code'`; second runner-up (REJECTED): add two actions `'propose_hypothesis'` + `'update_hypothesis'`. Tradeoff: my v1 of this decision rejected union expansion as unnecessary; codex correctly pointed out that conflation breaks two things: (i) policy expressiveness — an operator wanting `read_only_evidence` code reads but NO AI hypothesis authoring (e.g. a strict audit-mode scan where the AI's writes-to-internal-state are themselves excluded) has no way to express that under `read_code` reuse; (ii) audit trail clarity — the loop-trace's per-row gate decision would show `read_code` for a hypothesis authoring action, mislabeling the capability used. Two new actions (propose + update) would also expand the union but for no policy benefit, since both share the same authoring-shaped capability. ONE action (`author_hypothesis`) is the minimum union expansion that closes the codex finding. Default policies for all three modes (`read_only_evidence`, `sandbox_active_validation`, `approved_production_safe`) add `'author_hypothesis'` to `allowed_actions` so default operator scans behave identically to today; an operator can construct a custom policy that omits it for the strict-audit scenario. Both hypothesis tool descriptors register with `required_action: 'author_hypothesis'`. V8b (new) tests that a policy WITHOUT `'author_hypothesis'` denies both tools at the policy gate before `tool.invoke` runs. Roadmap open item #3 is resolved by THIS decision (not the v1 rejection).

- **Decision F (disposition states — Phase-2 enum vs. fresh small set): fresh closed union `HypothesisDisposition = 'proposed' | 'partially_evidenced' | 'evidenced_against' | 'superseded'`.** Runner-up (REJECTED): import / extend the `src/types/hypothesis.ts` lifecycle vocabulary. Tradeoff: same logic as Decision A — Phase-2 `Hypothesis` does not carry a disposition; the AI Inference Agent's lifecycle was `proposed → granted/denied context → fact-emitted`. The loop needs a smaller, observation-anchored vocabulary: `proposed` (initial state), `partially_evidenced` (some accepted facts referenced the hypothesis but it's not yet resolved), `evidenced_against` (accepted facts contradict the hypothesis), `superseded` (the AI replaced it with a refined hypothesis, linking via `supersedes_hypothesis_id?`). NO `confirmed` / `proven_*` / `launch_blocker` vocabulary — those are floor-only classification outputs, and the trust model forbids the AI from authoring verdicts (CLAUDE.md §Output language). `assertExhaustiveHypothesisDisposition` keeps future extensions honest. The disposition is the ONLY closed union in 40e; `control_id_hint?: string` and `briefing_field_ref?: string` stay open per FPP §2A.

- **Decision G (`view.hypotheses` shape — array vs. map): `readonly LoopHypothesis[]` ordered oldest-first by `proposed_at`.** Runner-up (REJECTED): `ReadonlyMap<HypothesisId, LoopHypothesis>`. Tradeoff: `LoopView` is hashed into `state_view_digest` (the per-row audit hash 40d's V7 explicitly covers); an array's JSON serialization is canonical (insertion order = chronological), while a `Map`'s JSON.stringify produces `{}` and requires a custom serializer — every consumer would need to convert. Array also matches the existing `view.facts: readonly NamedFact[]` shape (also chronological). Lookup by id is O(n) but the registry itself owns the fast lookup; the loop view is purely the AI's read surface, where n is small (single-digit hypotheses per scan in the Phase-3 budget envelope).

- **Decision H (loop-trace integration — terminal-row carry, NOT post-hoc row-0 mutation; codex 40e-row0-hypothesis-count-breaks-append-only-trace [APPLIED]): tool-call rows only PLUS one optional field on the TERMINAL row (`hypothesis_count` set on the `done` / `early_done` / `budget_halt` / `stall_halt` / `driver_error` row at scan end).** Runner-up (REJECTED): mutate row 0 post-loop with the final count. Tradeoff: codex caught that `LoopTraceWriter` is explicitly append-only per-step (PLAN §F + `loop-trace-writer.ts:1-15`); the 40d row-0 `briefing_digest` worked because the briefing is synthesized BEFORE the first trace row is emitted (digest known up-front, set on snapshot before the row writes). The final hypothesis count is only known AFTER the loop runs — there's no append-only path to put it on row 0 without violating the writer contract. The clean fix: attach `hypothesis_count` to the terminal row instead (which is the LAST row appended; the loop has already reached termination so the count is known). The trace-writer's existing terminal-row emit path takes one optional `hypothesis_count` parameter; the snapshot mutable already carries `briefingDigest` (40d pattern), so adding a sibling `hypothesisCount` field with the same one-time-emit semantics is symmetric. Decisions H + Produces + V12 + V14 + Done-When are all updated to "terminal row" instead of "row 0".

- **Decision I (persistence — when + where): `hypotheses.json` sibling to `project-briefing.json` + `cleanup-proof.json` + `http-write-registry.json`, written at scan end in `scan-command.ts` after the loop returns (same hook as 40c-v3's cleanup-proof persist block at `:1730`).** Runner-up (REJECTED): persist incrementally on every registry mutation. Tradeoff: hypotheses are not durable in the sense cleanup-proof is — they have no operational continuity requirement beyond audit. One canonical end-of-scan snapshot matches 40d's `project-briefing.json` shape and produces the byte-identical-across-reruns artifact V1 requires. Incremental writes would race the loop's per-step audit emit and require a fsync per mutation. Persistence is best-effort: a write failure logs once and proceeds (failure isolation per CLAUDE.md "Working with Claude" + 40d Decision E precedent); registry state at scan end IS what persists (mid-loop mutations are reconstructible from `loop-trace.jsonl` tool-call rows).

- **Decision J (report rendering — footer pointer vs. section): footer pointer only, mirroring 40d Decision G.** Runner-up (REJECTED): add a "Hypotheses" section to `agentic-report.ts`. Tradeoff: surfacing AI-authored hypothesis statements in the markdown report invites operators to read them as findings ("the AI says my app is likely missing X"). The trust model is absolute: only the floor produces findings, only findings render as report content. A one-line footer reference under "Scan metadata" (`Hypotheses: hypotheses.json (N proposed, M evidenced_against)`) gives operators audit visibility without conflating AI authoring with classification. 40g may revisit this once `priority_score` / `rationale_excerpt` ship and a unified "AI reasoning" section becomes the natural surface — explicitly deferred here.

- **Decision L (hypothesis-tool RESULTS must NOT flow into facts / ledger / floor; codex 40e-plan-02 [APPLIED]): propose-hypothesis and update-hypothesis tool descriptors return `{facts: []}` — the AI-facing handle is `view.hypotheses` on the next iteration, NOT a fact.** Runner-up (REJECTED): return `{facts: [{name:'hypothesis_id', value: <id>}, ...]}` (the v1 wording). Tradeoff: codex caught that any non-empty `facts` array on an accepted tool result flows into `acceptedByTool` → `collectAcceptedFacts()` → `view.facts` → the deterministic floor's predicate inputs. That would mean the AI-authored hypothesis acknowledgement (an ID + a disposition string) becomes an EVIDENCE fact — exactly what REVISION_AI_SHAPE §8 constraints 7, 8, and 10 forbid (the floor's input must remain accepted scanner / connector facts, not AI orchestration acknowledgements). The clean fix is empty-facts returns: the tool descriptor still records `tool_accepted` in the loop trace (audit visibility), the registry mutation still surfaces on the next `view.hypotheses` projection (the AI's read channel), but `collectAcceptedFacts()` sees nothing new from the hypothesis tools. V3b (new) explicitly tests "after one accepted propose-hypothesis, `view.facts.length` is unchanged from pre-call." There is NO need for a per-descriptor `feeds_floor` boolean — empty-facts returns are already the loop's well-defined contract for "this tool did its work but produced no evidence."

- **Decision M (`step_refs` grounding requirement for evidence-bearing dispositions; codex 40e-plan-03 [APPLIED]): when `update-hypothesis` sets disposition to `'partially_evidenced'` or `'evidenced_against'`, `step_refs` MUST be non-empty AND each ref MUST be a valid sequence number from an accepted loop step.** Runner-up (REJECTED): allow disposition changes with empty / unvalidated `step_refs`. Tradeoff: smart-orchestration roadmap row 2 explicitly says "AI marks `partially_evidenced` when accepted facts reference the hypothesis" — without a step-ref grounding check, the AI could author "I've now evidenced this hypothesis against control X" with zero actual evidence behind the disposition transition, and the report footer count (`M evidenced_against`) would display unverified state. The fix: a closure-injected `isAcceptedStepRef(seq: number): boolean` read against `ArtifactState.records()` (which already knows which seqs landed as `tool_accepted`). `update-hypothesis` invoke calls `isAcceptedStepRef` for every entry in `step_refs` when disposition ∈ `{'partially_evidenced', 'evidenced_against'}`; any miss → `Result.err(UnknownStepRefError)`, registry untouched. `'proposed'` (initial) and `'superseded'` (AI-revision-only) don't require step_refs. V5b (new) explicitly tests valid vs. unknown step refs.

- **Decision K (unresolved-hypothesis disposition — implement floor rule now vs. explicit defer; codex 40e-roadmap-open-hypothesis-disposition-missing [APPLIED]): EXPLICITLY DEFER the roadmap row 2 "floor emits coverage_gap on unresolved open hypothesis" behavior to 40g.** Runner-up (REJECTED): implement the deterministic floor rule in 40e. Tradeoff: the roadmap describes a floor-side hypothesis-aware predicate that promotes "AI proposed hypothesis X with no resolution" into a `coverage_gap` finding via the deterministic floor. Implementing it inside 40e would (i) make 40e's import-graph guard (V8) more complex — the floor predicate would need to read `view.hypotheses`, which means `src/cli/floor-predicates.ts` imports `LoopHypothesis` (still layer-safe but couples concerns) — and (ii) couple the hypothesis-registry step with classification-emission behavior, blurring the "registry is metadata, NOT evidence" split this step is built around. Until 40g lands the priority/rationale machinery that gives the AI an explicit reason to RESOLVE its hypotheses (mark `evidenced_against` / `partially_evidenced` / `superseded`), every scan would emit one coverage_gap per AI-authored hypothesis, which is exactly the "AI text becoming finding classification" failure mode REVISION_AI_SHAPE §8 forbids. The cleaner phasing: 40e ships the registry + persistence; 40g adds the floor-side reader once the AI has hypothesis-resolution mechanics. Until 40g lands, `hypotheses.json` is audit-only — operators can see what the AI hypothesized, but the report renders no derived finding from those entries. V14b explicitly tests "an unresolved `proposed` hypothesis at scan end does NOT produce a coverage_gap finding"; once 40g lands, that V14b assertion flips to the opposite (predicate-emits-coverage_gap-for-unresolved) as part of 40g's scope.
